# count-kcal-bot

Telegram-бот: текст или фото еды → калории и БЖУ, дневник по дням в SQLite. Что умеет и как запустить — README.

## Проверки

```bash
npm run typecheck && npm run lint && npm test
```

Тесты не ходят в сеть: `.env.test` — заглушки и база в памяти. Бот целиком проверяет `bot/create-bot.test.ts`
через `bot/fake-telegram.ts` и подменённый `fetch`.

**Не запускать бота с настоящим токеном из `.env` без спроса:** он уже работает на сервере — будет `409 Conflict`,
а ещё тратит DeepSeek и пишет в `kcal.db`.

## TypeScript без сборки

Node 24 запускает `.ts`, просто вырезая типы. Поэтому: в импортах расширение `.ts`; типы — только через `import type`;
нельзя `enum`, `namespace` и parameter properties (`erasableSyntaxOnly` в tsconfig).

## Устройство

- `bot/` — Telegram (grammY): по `Composer` на функцию бота в `features/`. `album.ts` собирает альбом в `ctx.album`
  до `sequentialize`, иначе фото альбома ждали бы друг друга в очереди.
- `recognition/` — текст или фото → продукты с КБЖУ: клиент DeepSeek, промпт, проверка JSON от модели.
- `products/` — штрихкод (zxing-wasm), поиск товара: кэш → Open Food Facts → Роскачество, пересчёт порции.
- `db/` — единственное место с SQL. `utils/` — дни в таймзоне, строки.

Правила:
- Вызовы только вниз: `bot/` → `recognition/` → `products/` → `db/` → `utils/`; вверх — лишь `import type`.
- `process.env` читает только `config.ts` — там же проверка при старте.
- `hide-token-in-logs.ts` — первый импорт в `main.ts`: в ошибках grammY URL с токеном бота.
- Обработчики не ловят ошибки сами: `AiError` и остальное долетает до `bot/error-handler.ts`.
- Тесты рядом с кодом (`x.ts` → `x.test.ts`), общие товары — `products/test-fixtures.ts`.
- Миграции — только дописывать в конец `MIGRATIONS`, выпущенные не править. `NOT NULL` снимается лишь
  пересозданием таблицы (образец — миграция 3). Колонки базы → camelCase через `AS`.
- Тексты для людей — слова полностью, с правильным склонением (`pluralize` в `utils/text.ts`).

## Поведение, сделанное так намеренно

- **Фото:** штрихкод локальным декодером → товар из кэша или баз (числа с упаковки, без нейросети) → иначе фото
  в нейросеть. Если модель разглядела цифры под штрихкодом — проверить контрольную цифру и искать снова, только
  если это новый код. Шаги передаются в `recognizePhoto` параметром — порядок тестируется без сети.
- **Open Food Facts раньше Роскачества:** числа полями надёжнее регулярок по тексту. Нет калорий в первой —
  спрашивается вторая.
- **Товар без калорий:** нейросеть оценивает на 100 г по названию и составу, оценка ложится в кэш
  (`nutrition_estimated`) — следующий скан без запроса. Кэш свежий 90 дней; если базы недоступны, берётся устаревший.
- **Продукт без калорий не записываем** — он испортил бы итог дня. Остальное из сообщения сохраняем, а его называем
  и просим уточнить (`save-entry.ts`). Не оценён ни один — не записываем ничего и объясняем, что сделать.
  Неизвестное БЖУ при известных калориях — «?» у продукта, в сумму не входит.
- Под записью — откуда числа; для Роскачества всегда ссылка на карточку (условие их API), превью ссылок выключено.
- Все фото альбома — одна запись и один запрос к нейросети: модель не задваивает упаковку, снятую с двух сторон.
- День — по времени отправки сообщения в `TZ`, а не по часам сервера.
- Тот же текст за 30 минут — записать, но предупредить о дубле. Только для текста: фото хранятся как «📷 фото».
- Текст длиннее 1500 символов в нейросеть не уходит.
- Название товара и текст записи — без кавычек вокруг: внутри бывают свои «».

## Внешние API (проверено 2026-10)

**DeepSeek:** модель `deepseek-flash` (текст и картинки); `deepseek-chat` — устаревший алиас.
`thinking: { type: 'disabled' }` — иначе размышления съедают `max_tokens`. Картинка —
`{ type: 'image_url', image_url: { url: 'data:image/jpeg;base64,…' } }` только в `user`; PNG и несколько картинок
в одном сообщении работают; `detail: 'low'` сжимает до 512 px — не для этикеток. `response_format: json_object`
работает вместе с картинкой, в промпте нужны слово «JSON» и пример. Расход токенов — на platform.deepseek.com.

**Open Food Facts:** `GET world.openfoodfacts.org/api/v2/product/<код>.json?fields=…`, 404 — товара нет;
`nutriments.*_100g` бывают строками. Условия: описательный `User-Agent`, один запрос = одно сканирование (отсюда кэш).
Поиск `/api/v2/search` жёстко ограничен по частоте.

**Роскачество:** `GET rskrf.ru/rest/1/search/barcode?barcode=<код>`, без ключа; нет товара — `{ response: {} }`.
Первый запрос → 302 с `Set-Cookie: __hash_=…`, повторить с cookie (`redirect: 'manual'`). КБЖУ — текстом
в `product_info` («Дополнительная информация»), у многих карточек его нет; без ккал считаем по 4/9/4.
Встреченные форматы — в `roskachestvo.test.ts`; новый формат из лога «товар есть, КБЖУ не распознано» добавлять туда.

**Отвергнуты:** Честный знак (ключ только участникам маркировки), barcode-list.ru (парсинг HTML, только названия),
Dietagram, FatSecret, Edamam, food-bd (лимиты или платно).

## Подводные камни

- **zxing-wasm:** в Node `.wasm` отдавать самим — `prepareZXingModule({ overrides: { wasmBinary } })`, путь через
  `import.meta.resolve`. Формат на вход `'EAN-13'`, в результате `'EAN13'`.
- **node:sqlite:** строки с null-прототипом (в тестах сравнивать `{ ...row }`); `new DatabaseSync` на несуществующий
  путь молча создаёт пустую базу; бэкап — `backup()`, а не `cp`: при WAL свежие записи лежат в `-wal`.
- **grammY runner:** `stop()` не ждёт обработчики — ждём сами по `runner.size()`. Ошибку обработчика отдаёт
  в `bot.errorHandler`, а `bot.handleUpdate` её пробрасывает — `fake-telegram.ts` делает как runner.
  При 401/409 падает сразу.
- **Альбом** приходит отдельными апдейтами с общим `media_group_id`; подпись обычно у одного фото.
- **typescript-eslint:** промис от `test()` разрешён через `allowForKnownSafeCalls` (`node:test`).
- **Telegram:** фото сжато до ~1280 px (картинка файлом — нет); URL файла содержит токен; сообщение до 4096 символов.

## Выкат и сервер

- Push в `master` → `.github/workflows/deploy.yml`: проверки → `rsync` в `/opt/count-kcal-bot` →
  `docker compose up -d --build`. Серверу не нужен доступ к GitHub.
- `.env` — только на сервере; база — на томе `data` (`/app/data/kcal.db`), переживает пересборку.
- `compose.yaml`: `stop_grace_period: 75s` (бот дорабатывает начатое до 70 с), ротация логов 3 × 10 МБ.
- Порты боту не нужны: он сам опрашивает Telegram. Порты Docker (`ports:`) обходят `ufw`.
- Бэкап — cron root на сервере (вс 21:00 UTC), копии в `/var/backups/count-kcal-bot`, 30 недель:
  ```
  0 21 * * 0 (cd /opt/count-kcal-bot && docker compose exec -T bot node scripts/backup-db.ts /app/data/backups && docker compose cp bot:/app/data/backups/. /var/backups/count-kcal-bot/ && find /var/backups/count-kcal-bot -name 'kcal-*.db' -mtime +210 -delete) >> /var/log/count-kcal-bot-backup.log 2>&1
  ```

## Идеи на потом

- Сообщение, отправленное в ту же секунду после альбома (например, `/undo`), обработается раньше альбома: альбом
  ждёт секунду до `sequentialize`. Если начнёт мешать — ставить сообщения пользователя в очередь за его альбомом.
